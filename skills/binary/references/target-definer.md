# Binary 目标定义 (Target Definer): 专家看到二进制文件时的第一直觉

> 在二进制世界里，你面对的不是源代码，是机器指令对内存的直接操控。
> 你的任务不是读每一行汇编，是标记出那些"外部不可信数据进入可信内存操作"的边界——
> 每一个边界都是潜在的突破口。

## 触发器：什么景象让 Binary 专家立刻警觉？

### 触发器一：看到危险函数在导入表中

**你的第一眼反应**："这个程序调用了 strcpy、sprintf、gets——这些都是内存安全的弃儿。"

`readelf -s` 或 `rizin -i` 输出中出现了 `strcpy`、`sprintf`、`gets`、`scanf`（无长度限制版本）——这是栈溢出的温床。

**立即追问链**：
1. 这些危险函数的调用点在哪里？（用 `rizin -a` 或 `grep` 找 xrefs）
2. 源缓冲区是否来自用户可控输入？（文件读取、网络接收、环境变量）
3. 目标缓冲区是在栈上、堆上、还是全局数据区？
4. 如果目标在栈上，返回地址与缓冲区的距离是多少？能否覆盖返回地址？
5. 如果目标在堆上，是否有堆元数据可被篡改？（size、fd、bk 指针）
6. 程序是否开启了 Stack Canary / NX / ASLR / PIE / RELRO？这些安全机制如何影响利用路径？

### 触发器二：看到 `malloc(n)` 中 n 来自用户输入

**你的第一眼反应**："如果用户传一个极大的数，malloc 会失败或分配极小的缓冲区；如果传一个负数，整数溢出会让分配比预期小。"

看到 `malloc(user_size)` 或 `malloc(strlen(user_input))`——这是堆溢出/整数溢出的信号。

**立即追问链**：
1. `user_size` 是否经过校验？最大允许值是多少？
2. 是否可能发生整数溢出？例如 `malloc(count * sizeof(element))`，如果 `count` 来自用户且未校验
3. `malloc` 的返回值是否被检查？如果分配失败返回 NULL，后续写入是否会导致空指针解引用？
4. 分配的缓冲区大小与实际写入的大小是否一致？是否存在 `off-by-one` 或 `off-by-many`
5. 堆分配后是否有 `memset` 初始化？未初始化的堆内存是否可被信息泄露利用？

### 触发器三：看到 `free(ptr)` 后 ptr 仍被使用

**你的第一反应**："这个指针被释放后有没有置 NULL？其他代码路径是否还保存着它的别名？"

看到 `free(ptr)` 后，同一函数或全局变量中仍有对 `ptr` 的访问——这是 Use-After-Free (UAF) 的信号。

**立即追问链**：
1. `ptr` 被释放后是否被置 NULL？
2. 是否有其他变量（别名）也指向同一块内存？
3. `ptr` 所在的结构体是否被缓存在容器（如链表、数组、哈希表）中？
4. 释放后、重用前的时间窗口有多大？攻击者能否控制这段时间内发生的堆分配？
5. 如果重用前分配了新的对象，新对象的数据是否能控制 UAF 时读取/写入的内容？

### 触发器四：看到 `printf(user_input)` 或类似模式

**你的第一反应**："格式化字符串的格式参数来自用户？这等于把内存的读取权和写入权交给了用户。"

看到 `printf(buf)`、`fprintf(file, buf)`、`syslog(LOG_INFO, buf)`，其中 `buf` 来自用户输入——这是格式化字符串漏洞的信号。

**立即追问链**：
1. 格式化函数的第一个参数（格式字符串）是否来自用户可控输入？
2. 如果是 `printf(buf)` 而非 `printf("%s", buf)`，攻击者可以通过 `%s`、`%n`、`%p` 等格式说明符读取/写入任意内存
3. 程序是 32 位还是 64 位？64 位下格式化字符串利用需要不同的技巧（参数通过寄存器传递）
4. 是否有 ASLR？格式化字符串可用于泄露栈地址、libc 地址，为后续 ROP 做准备
5. 是否有 FORTIFY_SOURCE？某些格式化字符串调用可能被编译器替换为安全版本

### 触发器五：看到用户输入进入 `system()` / `exec()` / `popen()`

**你的第一反应**："用户输入直接进入 shell？这是命令注入，不是二进制漏洞，但在二进制中同样致命。"

看到 `system(user_input)`、`popen(user_cmd)`、`execvp(argv[0])`——这是命令注入的信号。

**立即追问链**：
1. 用户输入是否经过过滤？过滤逻辑是否可被绕过？
2. 是否使用 `execve` 而非 `system`？（`execve` 不经过 shell，注入难度更高）
3. 是否使用白名单而非黑名单？（黑名单几乎总是可被绕过）
4. 环境变量是否可被用户控制？（PATH、LD_PRELOAD 等）

## 攻击面地图：Binary 全链条审计清单

| 链条环节 | 目标位置 | 审计焦点 | 典型漏洞 |
|---------|---------|---------|---------|
| **文件 I/O 边界** | `fopen`/`fread`、`mmap`、配置解析器 | 文件格式解析、Magic Number 检查、大小字段校验 | 缓冲区溢出、整数溢出、路径穿越 |
| **网络 I/O 边界** | `socket`/`bind`/`listen`、`recv`/`recvfrom` | 协议帧解析、长度字段、状态机转换 | 堆溢出、UAF、格式化字符串 |
| **环境/CLI 边界** | `getenv`、`argv`、`getopt` | 输入长度、特殊字符、环境变量继承 | 命令注入、栈溢出 |
| **IPC 边界** | 管道、共享内存、消息队列 | 权限校验、序列化/反序列化 | 权限提升、信息泄露 |
| **内存管理** | `malloc`/`free`、`new`/`delete` | 分配大小来源、释放后使用、双重释放 | 堆溢出、UAF、双重释放 |
| **字符串处理** | `strcpy`/`sprintf`/`strcat` | 源长度 vs 目标容量、终止符处理 | 栈溢出、堆溢出 |
| **格式化输出** | `printf`/`fprintf`/`syslog` | 格式参数来源 | 格式化字符串漏洞 |
| **整数运算** | 长度计算、索引计算、大小字段 | 有符号/无符号转换、乘法溢出、截断 | 整数溢出 → 缓冲区溢出 |

## 安全机制检查清单

对每个目标二进制，首先执行：

```bash
# 检查安全机制
checksec --file=./target_binary

# 期望输出解读
# NX enabled     → 栈/堆不可执行，需要 ROP/JOP
# PIE enabled    → 基地址随机化，需要信息泄露
# Stack Canary   → 栈溢出覆盖返回地址前会被检测
# ASLR enabled   → 系统级地址随机化
# RELRO Full     → GOT 表不可写
# RELRO Partial  → GOT 表可写，可通过格式化字符串覆盖
# FORTIFY_SOURCE → 某些危险函数被编译器替换为安全版本
# Stripped       → 无符号信息，逆向难度增加
```

**安全机制对利用路径的影响**：

| 安全机制 | 被保护的目标 | 绕过思路 |
|---------|-----------|---------|
| NX | 栈/堆代码执行 | ROP / ret2libc / JOP |
| ASLR + PIE | 代码/数据基地址 | 信息泄露（格式化字符串、UAF）|
| Stack Canary | 栈返回地址 | 泄露 Canary 值 / 不覆盖返回地址的攻击（如劫持函数指针）|
| RELRO Full | GOT 表 | 无法覆盖 GOT，需找其他可写函数指针 |
| RELRO Partial | GOT 表 | 格式化字符串覆盖 GOT 条目 |
| FORTIFY_SOURCE | 危险函数调用 | 找未被替换的调用点，或绕过检查逻辑 |

## 输出要求

1. **攻击面地图**：列出所有外部输入边界（文件/网络/环境/CLI），标注用户可控的数据流向
2. **Taint Source 清单**：标记所有"脏"变量（用户可控输入）及其传播路径
3. **安全机制评估**：`checksec` 输出解读，标注哪些机制被启用/禁用
4. **高价值目标清单**：按 P0/P1/P2 排序的函数/地址列表，附带触发理由
