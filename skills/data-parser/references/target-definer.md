# 目标定义者 (Target Definer): 锁定脆弱的状态枢纽

不要用找 SQL 注入的思维来看解析器。你需要找到那些负责将二进制流或文本转换为内存对象的最底层入口。

## 专家的审计锁定点

你必须精准搜寻并在代码中标记以下“事故多发地段”：

### 1. 寻找“内存分配”的数学算式
*   全局搜查所有的 `malloc`, `realloc`, `calloc`, 或者 C++/Rust/Go 中的 `new`, `make()`, `[]byte(nil)` 等资源分配动作。
*   追踪这些分配调用的参数 —— 它是由哪个外部输入的 `length` 或 `count` 控制的？
*   **关键疑问**：在执行加法或乘法前，是否使用了 Checked Arithmetic（防溢出算术判断）？

### 2. 寻找“循环与嵌套”的状态器
*   找出处理类似 List/Array, Object/Map/Dict 的迭代函数（通常是 `parse_array()`, `parse_object()`）。
*   **关键疑问**：这个循环是否有 `MAX_DEPTH` (最大嵌套深度) 限制？如果是递归调用，是否有计数器跟踪栈的深度？

### 3. 寻找“指针/数组偏移”的微观操作
*   寻找形如 `*ptr++`, `buffer[offset]`, `view.slice(start, end)` 的地方。
*   **关键疑问**：这个 `offset` 如果超出整个物理缓冲区 (`buffer.length`)，会有 assert/exception 阻挡吗？

### 4. 寻找“类型与反射”入口 (Polymorphic Entrypoints)
*   如果库支持多态（动态识别加载类），找到反射调用 `Class.forName()`, `Method.invoke()`, 或反序列化 `readObject() / unmarshal()` 的入口配置点。
*   **关键疑问**：是否存在“白名单/黑名单”配置项来约束它能实例化什么类？默认配置是否安全？

## 你的目标输出
建立一张解析路线图：
**[外部输入字节流]**  ---->  **[分配器/长度解码单元/类型反射器]**  ---->  **[生成的 AST/内存对象]**。
并标记出可能没有对“恶意的元数据长度”实施防守的代码行。
