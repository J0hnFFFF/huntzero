# 解析器 PoC 生成 (PoC Generator): 用最小输入触发最大破坏

> 一个优秀的 PoC 不是越复杂越好，而是越短、越稳定、越不可辩驳越好。
> 你的目标是把 10MB 的崩溃输入压缩到 10 字节，让开发者无话可说。

---

## 触发器：什么发现让 PoC 专家立刻开始最小化？

### 触发器一：Fuzzer 发现了一个崩溃输入

**你的第一眼反应**："这个输入有 90% 是噪声，找到真正触发崩溃的那几个字节。"

模糊测试生成的语料往往包含大量冗余。最小化（Minimization）是提取核心触发模式的关键步骤。

**立即追问链**：
1. 崩溃是否稳定复现？运行 10 次是否 10 次都崩溃在同一位置？
2. 输入的哪一部分控制了崩溃地址？尝试用 `0x41`（A）和 `0x42`（B）替换不同区域。
3. 使用 Delta Debugging 或 fuzzer 自带的最小化工具（如 AFL 的 `afl-tmin`）能压缩到多少？
4. 如果崩溃依赖于特定长度字段，尝试将长度改为相邻值（±1），确认边界。
5. 去除输入中不影响崩溃的字节后，是否仍能触发相同类型的崩溃（SIGSEGV 等）？
6. 最小化后的输入是否仍然满足协议/格式的基本语法要求？还是已经进入非法状态？

### 触发器二：手动构造的载荷触发了异常行为

**你的第一眼反应**："逐步删除字段，确认哪个字段是触发异常的最小充分条件。"

手动构造的载荷通常包含多个攻击向量的组合，需要分离出单一触发因子。

**立即追问链**：
1. 载荷中是否包含多个可疑字段？逐个注释/删除，观察异常是否持续。
2. 如果涉及嵌套深度，最小深度是多少？从 1 层开始递增，找到临界点。
3. 如果涉及长度字段，最小触发长度是多少？尝试 0、1、最大值、最大值-1。
4. 是否需要特定的前置上下文（如文件头、Magic Number）才能到达脆弱代码路径？
5. 输入中的字节序（大端/小端）是否影响脆弱代码的触发？
6. 是否能构造一个完全 printable 的 PoC？（避免二进制字符被邮件系统或终端破坏）

### 触发器三：崩溃发生在复杂解析流程中

**你的第一眼反应**："找到进入脆弱代码路径的最短语法树。"

某些漏洞只在解析特定复合结构时触发，如 JSON 对象内的数组内的字符串。

**立即追问链**：
1. 脆弱代码位于哪个解析阶段？词法分析、语法分析、语义验证、还是后处理？
2. 是否需要前置的合法结构才能到达该阶段？如是否需要先打开一个对象 `{`？
3. 最小触发路径是否可以表示为 BNF 语法片段？如 `OBJECT ::= '{' STRING ':' VULNERABLE_TYPE '}'`
4. 是否存在多种语法路径到达同一代码位置？哪种路径所需的输入最短？
5. 解析器是否支持注释或空白字符？这些是否可以任意插入而不影响触发？
6. 如果目标是通过网络接收输入，PoC 是否需要包装在特定协议帧中（如 HTTP Body）？

### 触发器四：崩溃无法稳定复现

**你的第一眼反应**："这不是随机噪声，而是堆布局或线程竞争导致的时序依赖。"

不稳定复现不代表不可利用，但需要更深入的分析来固定条件。

**立即追问链**：
1. 崩溃是否只在特定堆布局下发生？尝试在 PoC 前插入大量分配/释放操作来稳定布局。
2. 是否涉及多线程竞争？尝试减少线程数或使用 `taskset` 绑定到单核。
3. 是否使用 AddressSanitizer (ASan) 运行？ASan 往往能捕获更早期的内存错误并稳定复现。
4. 目标是否使用了自定义内存池？尝试操控池内对象的分配顺序。
5. 是否存在时间窗口极小的竞争条件？如 `free` 和 `deref` 之间只隔几条指令。
6. 如果确实无法 100% 复现，统计复现概率并计算期望尝试次数（如 1/10 则期望 10 次）。

### 触发器五：需要向非技术受众演示漏洞

**你的第一眼反应**："PoC 必须是一行命令就能运行的脚本，而不是一个复杂的构建流程。"

向管理者、客户或安全团队报告时，可执行的一键 PoC 最有说服力。

**立即追问链**：
1. PoC 是否包含所有依赖（或明确列出安装命令）？避免 "pip install xxx" 失败的尴尬。
2. 是否提供两种形式：原始二进制输入（hexdump）和自动化发送脚本（Python/Go）？
3. 是否包含明确的预期输出说明？如 "运行后 3 秒内应看到 Segmentation fault"。
4. 如果目标需要网络交互，PoC 是否内嵌了简单的服务端/客户端？
5. 是否考虑了不同操作系统（Linux/macOS/Windows）的可移植性？
6. 是否提供了 `README` 说明漏洞原理、影响版本和临时缓解措施？

## 攻击链闭合：从原始输入到最小 PoC 的完整流程

```
[AFL 生成 4KB 崩溃语料]
    → [运行 afl-tmin 压缩到 120 字节]
    → [手动分析：确认前 4 字节是长度字段，值为 0xFFFFFFFF]
    → [尝试替换长度字段为 0x80000000、0x7FFFFFFF、0、1]
    → [确认 0x80000000 稳定触发，且为最小充分条件]
    → [构造最终 PoC：4 字节 + 8 字节填充 = 12 字节]
    → [编写自动化脚本，运行 100 次 100% 复现]
```

**闭合条件**：输入最小化 + 复现率 100% + 触发原因可解释。

## 典型代码模式与警觉点

### 脆弱 PoC：原始 fuzzer 输出（冗余）
```
# 原始 1024 字节 fuzzer 输出，大部分无关
00000000: 7b22 6e61 6d65 223a 2022 4141 4141 4141  {"name": "AAAAAA
00000010: 4141 4141 4141 4141 4141 4141 4141 4141  AAAAAAAAAAAAAAAA
...（980 字节重复）
```

### 安全 PoC：最小化后的输入
```python
# 最小 PoC：仅 12 字节触发整数溢出
import struct
import sys

poc = struct.pack(">I", 0x80000000)  # 声明 2GB 长度
poc += b"TRIG"                       # 4 字节魔术触发器

with open("poc.bin", "wb") as f:
    f.write(poc)

# 运行：./vuln_parser poc.bin
# 预期：3 秒内发生 SIGSEGV，崩溃地址 0xXXXXXXXX
```

### 脆弱 PoC：复杂的手动构造（难以复现）
```python
# 需要特定环境配置和前置步骤
def run_complex_poc():
    setup_database()
    create_user("admin")
    login("admin", "password")
    upload_file("stage1.bin")
    upload_file("stage2.bin")
    # ... 20 步后才能触发
```

### 安全 PoC：一键运行脚本
```python
#!/usr/bin/env python3
"""
PoC: CVE-XXXX-XXXX - VulnParser Integer Overflow
Tested on: VulnParser 1.2.3, Ubuntu 22.04
"""
import socket, struct, sys

def poc(host="127.0.0.1", port=9000):
    payload = struct.pack(">I", 0xFFFFFFFF) + b"A" * 8
    s = socket.socket()
    s.connect((host, port))
    s.send(payload)
    s.close()
    print(f"Sent {len(payload)} bytes. Check target for crash.")

if __name__ == "__main__":
    poc(*sys.argv[1:])
```

## 输出要求

1. **最小化输入**：hexdump 和原始二进制文件。
2. **复现脚本**：一键运行的 Python/Bash 脚本，含依赖说明。
3. **崩溃报告**：信号类型、崩溃地址、寄存器状态、栈回溯。
4. **原理摘要**：用不超过 3 句话解释为什么这个最小输入会触发漏洞。
