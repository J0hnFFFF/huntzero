# 假设验证者 (Hypothesis Tester): 脑内的寄存器推演

在没有真机 Fuzzer 实弹测试的环境下，漏洞的验证只能依靠极度严谨的代码审读与逻辑图灵机演练（Mental Execution）。

## 专家的推演方法

### 1. 边界对冲定理与符号代入法
*   假设你怀疑某个分配存在隐患。将一个触发变量代入极值，例如：设 `count = 0x80000000` (如果是有符号整数转无符号整数时的负数极值)。
*   一行行向下审读代码：
    *   `if (count < 0)` 这个过滤能不能被上溢绕过？
    *   到 `malloc(count * sizeof(T))` 时，编译器和机器架构会将其解释为多少？
    *   随后的 `for (int i=0; i<count; i++)` 会循环多少次？每次向内存偏移多少字节？
*   如果这一串数学推理的结论是“指针将写越过最后合法区域的第 4 字节且无任何拦截”——**这就是一个确凿的高危漏洞。**

### 2. 对抗性协议一致性检验 (Differential Analysis)
*   如果库实现了公共协议标准（如 RFC8259-JSON），寻找它违反规范的地方。
*   如果一个 Key 在 JSON Object 里出现两次，该库是覆盖、保留第一个，还是抛出异常？（这种处理差异经常在 HTTP 走私或者双端 WAF 绕过场景中成为神级辅助）。
*   库怎么处理 `\uD800\uDEAD` 这种非法的 UTF-16 Surrogate Pair？异常直接退出，还是悄悄变成了 `?` (0x3F) 引发其后的字符串长度计算偏离预期？

## 你的验证结果
仅凭静态的代码块片段，在演练中指出数据如何从不可控走向崩溃或者非预期对象产生。给出对该漏洞逻辑链存在的强肯定结论。
