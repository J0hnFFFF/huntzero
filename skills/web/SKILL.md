# Web 系统地形情报 (Web Domain Brief)

> [!IMPORTANT]
> 在 Web 的世界里，你面对的不是一个程序，而是一个**不断失忆又被迫重建记忆的对话系统**。
> 每一次 HTTP 请求都是一次**完整的身份代理** —— 浏览器替你携带凭证，但服务器永远无法确知：这是用户本人的意志，还是精心伪造的指令？
> V7 模式：本文件是 **领域地形知识**，不是执行步骤。Cerebrum 读取后应基于第一性原理自主决定分析路径。

## 第一性原理：黑客眼中的 Web 本质

Web 应用是一类以**无状态协议（HTTP）承载状态化业务**的分布式系统。其核心矛盾在于：

### 原理一：请求即代理的意志不确定性 (The Uncertainty of Request-as-Proxy)

每一次 HTTP 请求都携带了完整的身份凭证（Cookie/Token），但服务器永远无法确知：
- 这是用户**主动**发起的意志表达？
- 还是攻击者**诱导**浏览器/脚本发出的伪造指令？

**黑客视角**：重点不是"身份是否伪造"，而是**"服务器是否会在未确认用户意志的情况下执行不可逆操作"**。寻找那些"一发即中"的状态转换端点 —— 一个精心构造的请求一旦到达，副作用已经发生。

### 原理二：无状态协议的失忆困境 (The Amnesia of Stateless Protocol)

HTTP 协议本身不保存任何会话记忆。每一次请求都是孤立的，服务器被迫：
- 从请求中提取身份（Cookie/Header）
- 从请求中推断业务上下文（URL 参数、Body）
- 在毫秒级时间内完成授权决策

**黑客视角**：寻找**状态推断的断层** —— 当请求中携带的"当前状态"与服务器实际状态不一致时，是否存在被利用的窗口？（例如：Token 有效但用户已被禁用、订单已支付但请求携带待支付状态）

### 原理三：同源策略与跨域需求的结构性张力 (The Same-Origin Paradox)

浏览器安全模型建立在"同源即信任"的假设上，但现代 Web 业务天然需要：
- 跨域 API 调用（CORS）
- 第三方脚本嵌入（Analytics、Ads）
- 跨站点跳转（OAuth、SSO）

**黑客视角**：这不是寻找 XSS，而是寻找**信任边界的重构点** —— 当一个请求携带合法凭证流向"理论上可信"的第三方时，攻击者能否将自己插入这个信任链？（CORS 配置错误、postMessage 不校验来源、JSONP 回调劫持）

### 原理四：输入到状态转换的语义断层 (The Semantic Gap of Input-to-State)

Web 应用接收的是**文本**（URL 字符串、JSON、Form Data），但最终要转换为**内部状态**（数据库记录、文件系统操作、业务对象）。

这个转换链条上充满了语义扭曲的可能：
- URL 编码的多次解码差异
- Unicode 规范化前后的字符变化
- JSON 解析后的类型转换（数字变字符串）
- 文件名在不同文件系统的解释差异

**黑客视角**：寻找**语义不一致的转换节点** —— 安全检查在 A 层基于某种解释做判断，但实际操作在 B 层基于另一种解释执行。（路径穿越、编码绕过、类型混淆）

## 已知的结构性地形

### 地形一：单次请求的不可逆操作点

那些一旦执行就无法回滚的状态转换：
- 资金动账（转账、支付、退款）
- 权限变更（提权、角色授予、API Key 生成）
- 数据销毁（删除账户、清空记录、退订服务）

**分析焦点**：这些端点是否存在**预执行确认机制**？攻击者能否通过 CSRF 或预检请求绕过确认？

### 地形二：状态推断的断层带

服务器从请求中推断业务状态的脆弱区域：
- **IDOR 场景**：资源 ID 来自 URL 参数，服务器推断"用户想操作这个资源"，但并未验证用户是否拥有该资源
- **条件竞争**：请求 A 和请求 B 并发到达，服务器分别推断状态，但执行时的实际状态已改变
- **缓存污染**：CDN 或浏览器缓存层基于请求特征推断响应，但攻击者污染了这个推断

### 地形三：信任链的重构节点

跨域/跨站点交互的权限传递点：
- **OAuth 回调**：`state` 参数的验证是否完整？`redirect_uri` 是否严格匹配？
- **postMessage**：目标 `origin` 是否严格校验？消息内容是否被信任？
- **CORS 预检**：`Access-Control-Allow-Origin: *` 与 `withCredentials: true` 的危险组合
- **子域名接管**：被遗弃的子域名 CNAME 指向可被攻击者注册的服务

### 地形四：语义转换的扭曲点

输入文本到内部状态的转换链条：
- **路径规范化**：`/../`、空字节 `%00`、Unicode 等价字符（`%C0%AF` 替代 `/`）
- **类型混淆**：JSON 中 `"0"` vs `0`，表单中数组表示法 `key[]`
- **编码差异**：URL decode 次数、HTML 实体解码与 JavaScript Unicode 转义的交错
- **长度计算**：字符数 vs 字节数（多字节字符、组合字符）

## 已知的 Invariant 失效模式

| Invariant 声明 | 结构性失效原因 | 原理映射 |
|----------------|---------------|---------|
| "操作者必须拥有资源" | 服务器从请求参数推断资源归属，而非从会话状态查询 | 原理二：失忆困境 |
| "业务只能正向推进" | 请求携带的状态标记被信任，缺少与服务端实际状态的交叉验证 | 原理二：失忆困境 |
| "外部输入经过净化" | 净化逻辑基于某一语义层，但实际操作在另一语义层执行 | 原理四：语义断层 |
| "跨域请求受同源策略保护" | CORS 配置将信任扩展到攻击者可控的 Origin | 原理三：信任重构 |

## 项目类型对严重性的影响

> [!WARNING]
> 同样的代码缺陷在不同项目类型下严重性完全不同。

| 项目类型 | 示例 | 严重性调整 |
|---------|------|-----------|
| **Web 框架/库** | Express middleware, Django app | 漏洞需调用者传入恶意输入，严重性 **-1 级** |
| **部署服务** | 生产环境 API 服务、管理后台 | 网络可达，**标准严重性** |
| **API-Only 后端** | 纯 REST/GraphQL 无前端 | 关注认证/授权，XSS 相关性低 |
| **自托管开源项目** | 某已知漏洞, WordPress, GitLab | 用户运维导致配置风险更高 |

**Web 框架中**的 SSRF 是 LOW（需要框架使用者自己暴露），
**部署服务中**的 SSRF 是 HIGH（直接可利用）。

## 你的行为准则

作为 huntzero，在此领域：

1. **放弃输入验证思维**：不要寻找"哪里没有过滤特殊字符"，而是寻找**"请求中的身份与意图是否经过二次确认"**。

2. **关注状态推断的脆弱性**：每一次请求都在"声称"当前状态，你要问的是：**"如果请求中声称的状态是假的，服务器会做什么？"**

3. **追踪信任链的重构**：当一个携带用户凭证的请求流向第三方（跨域、跳转、嵌入），**"第三方能否被攻击者控制？"**

4. **寻找语义转换的错位**：安全检查在 A 层基于某种解释执行，但实际操作在 B 层执行 —— **这两层的解释是否一致？**
