# Web 漏洞挖掘 (Web Vuln Hunter)

基于 Web 系统的四大第一性原理，追踪结构性脆弱点。

## 核心分析框架

### 原理一：请求即代理的意志不确定性
**关键问题**：服务器能否区分用户主动意志 vs 攻击者诱导？

**追踪路径**：
- 寻找"一发即中"的不可逆操作端点（支付、删除、权限变更）
- 检查是否存在预执行确认机制，或能否被绕过
- 分析请求是否可被跨域/跨站点诱导（CSRF、JSONP、CORS）
- 验证：删除 Cookie/Token 后是否仍能执行关键操作？

### 原理二：无状态协议的失忆困境
**关键问题**：服务器从请求推断的状态，与实际状态是否一致？

**追踪路径**：
- 资源 ID 来自请求参数时，服务器是否验证"该用户拥有此资源"？
- 业务流程中，后置状态请求是否验证前置状态已完成？
- 并发场景下，多个请求推断的状态是否可能冲突？
- 检查：能否用已失效的身份凭证（过期 Token、已禁用账户）执行操作？

### 原理三：同源策略与跨域需求的张力
**关键问题**：信任边界在跨域交互中如何被重构？

**追踪路径**：
- 识别所有跨域交互点（OAuth、SSO、第三方嵌入、postMessage）
- 检查 `Origin`/`Referer` 验证的严格性
- 分析 CORS 配置是否过度放权（`Access-Control-Allow-Origin: *` + `withCredentials`）
- 检查子域名/相关域的可控性（是否存在被遗弃的 CNAME）
- 验证：能否将自己插入合法用户的跨域信任链？

### 原理四：输入到状态的语义断层
**关键问题**：安全层与执行层对输入的解释是否一致？

**追踪路径**：
- 追踪路径/文件名在多层处理中的解释差异（URL decode 次数、Unicode 规范化）
- 检查类型转换陷阱（JSON 数字 vs 字符串、表单数组表示法）
- 分析长度计算差异（字符数 vs 字节数、多字节字符）
- 验证：能否让安全层看到 A，但执行层实际执行 B？

## 分析方法论

### 逻辑流映射（非流程图，而是状态推断图）
不绘制业务流程，而是绘制**状态推断链**：
```
请求参数 resource_id=123 
    ↓ [推断点1：服务器认为这是"用户想操作资源123"]
查询数据库（但未验证ownership）
    ↓ [推断点2：服务器认为"这个查询结果是安全的"]
执行更新
```
**目标**：找到推断链上的断裂点 —— 哪里推断可能出错？

### 语义扭曲探测（非输入验证，而是解释差异）
针对同一输入，在不同层级注入解释差异：
- 路径：`/../../../etc/passwd` vs `%2e%2e%2f` vs `..%c0%af`
- 身份：并发请求携带冲突的状态标记
- 类型：JSON 中 `"0"` 被解释为数字 `0`

**观察**：安全层拒绝但执行层接受？或者反之？

### 跨域信任劫持（非 CORS 配置检查）
问自己：一个携带用户凭证的请求，能否被诱导流向攻击者控制的端点？
- 通过跳转参数（`?redirect=attacker.com`）
- 通过 postMessage 目标篡改
- 通过子域名接管
