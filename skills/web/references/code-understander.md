# Web 代码理解 (Code Understander): 破译服务器推断链的断裂点

> 供应链专家看的是工厂机器的权力分配。
> Web 专家看的是**服务器在毫秒间做出的所有推断**——
> 它从请求参数中推断用户身份、推断资源归属、推断业务状态、推断操作意图。
> 你的任务是：找到推断链上的断裂点。

## 触发器：什么代码结构让 Web 专家立刻进入深度审计模式？

### 触发器一：看到资源查询未绑定用户身份

**你的第一反应**："这个查询条件里没有 user_id，任何人传个 id 就能查。"

```java
// 警觉信号
return orderRepository.findById(id);  // WHERE id = ?
```

**深度追问链**：
1. 这个查询是在哪一层执行的？Controller / Service / DAO？
2. 查询条件中是否有 `AND user_id = ?` 或等效的所有权校验？
3. 如果这是一个通用查询方法（如 `findById`），是否有调用方在调用前做了所有权校验？
4. 是否所有调用路径都经过了这个校验？有没有 Admin 接口、内部 API、批量接口绕过了它？
5. 如果使用了 ORM（如 Hibernate、Django ORM），`@ManyToOne` 或 `@OneToMany` 的关联查询是否隐式暴露了其他用户的数据？

**攻击链闭合推演**：
```
Controller: GET /api/orders/{id}
    ↓
Service: orderService.findById(id)
    ↓
DAO: SELECT * FROM orders WHERE id = ?
    ↓
未校验 user_id → 返回任意 ID 的订单
    ↓
攻击者遍历 id=1,2,3... → 批量获取所有用户订单
```

### 触发器二：看到中间件/拦截器的顺序问题

**你的第一反应**："这个 CORS 中间件放在认证中间件前面还是后面？顺序错了等于没做。"

```javascript
// 警觉信号：CORS 在认证之后
app.use(authMiddleware);    // 先认证
app.use(corsMiddleware);    // 后 CORS —— 预检请求可能直接 401
```

**深度追问链**：
1. CORS 预检请求（OPTIONS）是否被认证中间件拦截？（导致浏览器无法获得 CORS 头）
2. 错误处理中间件是否在认证之前？（异常信息可能泄露给未认证用户）
3. 请求体解析中间件（body-parser）是否在安全校验之前？（大文件上传 DoS）
4. 日志中间件是否记录了敏感信息？（密码、Token、银行卡号）
5. 速率限制（rate limiter）是否在所有入口都生效？（包括文件上传、WebSocket、GraphQL）

**攻击链闭合推演**：
```
攻击者发送 OPTIONS 预检请求
    ↓
认证中间件拦截 → 返回 401 Unauthorized
    ↓
浏览器未收到 CORS 头 → 认为跨域被阻止
    ↓
但攻击者发送简单请求（GET with text/plain）
    ↓
认证中间件通过 → CORS 头返回 Access-Control-Allow-Origin: *
    ↓
攻击者的网页可以携带 Cookie 访问该 API
    ↓
简单请求和复杂请求的处理逻辑不一致 → 安全绕过
```

### 触发器三：看到客户端状态直接写入数据库

**你的第一反应**："客户端告诉服务器'状态是已完成'，服务器就直接 UPDATE 了？"

```python
# 警觉信号
order.status = request.json['status']  # 客户端直接控制状态
order.save()
```

**深度追问链**：
1. 状态字段是否来自客户端可控的输入？
2. 服务器在更新前是否查询了当前实际状态？
3. 是否存在状态机？能否从任意状态跳到任意状态？
4. 价格、金额、折扣是否由客户端提供？服务器是否独立计算？
5. 时间戳、签名是否由客户端生成？如何验证有效性？

**攻击链闭合推演**：
```
正常流程: pending → paid → shipped → completed
    ↓
攻击者发送: {"order_id": 123, "status": "completed", "price": 0.01}
    ↓
服务器直接 UPDATE orders SET status='completed', price=0.01 WHERE id=123
    ↓
未验证: 实际支付金额是否为 0.01？是否已发货？
    ↓
攻击者以 0.01 元"完成"了一笔原价 1000 元的订单
```

### 触发器四：看到跨域/第三方交互代码

**你的第一反应**："这个 postMessage/OAuth/CORS 的配置里，信任的边界在哪里？"

```javascript
// 警觉信号
window.addEventListener('message', (e) => {
    if (e.origin.includes('trusted.com')) {  // 包含而非精确匹配
        processMessage(e.data);
    }
});
```

**深度追问链**：
1. origin 校验是否使用精确匹配（`===`）而非包含匹配（`includes`）？
2. 消息内容是否经过 schema 校验？还是无条件信任并执行？
3. OAuth 的 `redirect_uri` 校验是精确匹配、前缀匹配还是正则匹配？
4. CORS 配置是静态白名单还是动态反射 Origin 头？
5. 第三方脚本（Analytics、Payment Widget）是否有 Subresource Integrity（SRI）校验？

### 触发器五：看到文件路径/命令拼接

**你的第一反应**："安全检查在 A 层做判断，实际操作在 B 层执行——这两层的解释一致吗？"

```python
# 警觉信号
filepath = UPLOAD_DIR + filename  # 用户可控 filename
os.system("convert " + filepath)  # 命令拼接
```

**深度追问链**：
1. 文件名是否经过路径规范化？`os.path.normpath`、`Path.resolve()`？
2. 文件扩展名校验是基于原始文件名还是规范化后的文件名？
3. URL 参数中的路径是否被 URL decode 多次？每次由哪一层处理？
4. 命令拼接中的用户输入是否被 shell 转义？使用参数列表还是字符串拼接？
5. 文件名中是否可能包含 Unicode 等价字符？

## 专家代码审计的深层视角

### 视角一：推断链追踪

对每个关键操作，追踪完整推断链：

```
[请求参数] resource_id=123
    ↓ [推断点1] 服务器认为"用户想操作资源123"
    ↓ [验证点1] 是否验证了用户拥有资源123？
    ↓ [推断点2] 服务器认为"当前状态允许此操作"
    ↓ [验证点2] 是否查询了数据库验证实际状态？
    ↓ [推断点3] 服务器认为"用户有权限执行此操作"
    ↓ [验证点3] 是否检查了角色/权限？
    ↓ [执行] 实际数据库操作
```

**审计规则**：每个推断点都必须有对应的验证点。没有验证点的推断 = 潜在漏洞。

### 视角二：语义层映射

追踪同一输入在不同语义层的解释：

| 语义层 | 输入示例 | 解释方式 | 潜在差异 |
|-------|---------|---------|---------|
| **URL 层** | `..%252f..%252fetc%252fpasswd` | URL decode 1 次 | `%25` → `%`，留下 `%2f` |
| **框架层** | `..%2f..%2fetc%2fpasswd` | URL decode 2 次 | `%2f` → `/` |
| **应用层** | `../../etc/passwd` | 路径规范化 | 可能解析为绝对路径 |
| **OS 层** | `/etc/passwd` | 文件系统打开 | 实际访问的目标 |

**审计规则**：如果安全校验在某一层执行，但实际操作在另一层执行 → 可能存在语义断层。

### 视角三：信任边界图

绘制请求处理流程中的信任边界：

```
[不可信] 客户端请求
    ↓
[半可信] CDN / WAF / 负载均衡（可能被绕过）
    ↓
[半可信] 框架中间件（CORS、Body Parser、认证）
    ↓
[可信] 应用控制器（应在此处完成所有身份/权限校验）
    ↓
[可信] 业务服务层
    ↓
[可信] 数据访问层
    ↓
[可信] 数据库 / 文件系统
```

**审计规则**：不可信输入必须在进入可信区域前完成所有校验。校验在不可信/半可信区域执行 = 可被绕过。
