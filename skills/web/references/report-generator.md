# Web 分析报告 (Report Generator)

## 报告核心结构

### 1. 结构性概览
不列漏洞数量，而描述**系统性假设风险**。

**内容**：
- **应用本质定位**：该系统属于哪种结构性类型？
  - 高价值交易类（支付、转账）→ 重点关注意志不确定 + 失忆困境
  - 多租户协作类（SaaS、云盘）→ 重点关注失忆困境 + 信任重构
  - 开放平台类（OAuth、API 网关）→ 重点关注信任重构 + 语义断层
  
- **四大原理风险评估**：
  | 原理 | 风险等级 | 核心证据 |
  |------|---------|---------|
  | 意志不确定性 | High/Med/Low | 关键不可逆操作是否可跨域诱导 |
  | 失忆困境 | High/Med/Low | 状态推断链的脆弱点分布 |
  | 信任重构 | High/Med/Low | 跨域交互点的信任边界完整性 |
  | 语义断层 | High/Med/Low | 输入处理层级的解释一致性 |

### 2. 假设断裂分析（非漏洞详情）
每个发现的结构性脆弱点按以下格式呈现：

```markdown
## 假设断裂点 #{ID}

### 被打破的假设
[描述服务器做出的错误核心假设]
示例："服务器假设携带有效 Token 的请求即代表用户本人的主动意志"

### 涉及的原理
[意志不确定 / 失忆困境 / 信任重构 / 语义断层]

### 推断链断裂位置
```
请求参数 resource_id=123 
    ↓ [推断点1] 服务器推断"用户想操作资源123"
查询数据库（未验证ownership）
    ↓ [推断点2] 服务器推断"该查询结果可安全返回"
返回敏感数据
```
断裂点：推断点1 —— 未验证用户是否拥有资源123的访问权限

### 验证证据
- **假设检验方法**：如何设计实验验证该假设是否成立
- **观察结果**：响应差异、状态变化、访问成功与否
- **对比分析**：正常请求 vs 恶意请求的服务器行为差异

### 业务影响（状态层面，非系统层面）
- **影响的状态**：哪些业务状态可能被错误改变？
- **影响的用户**：仅当前用户？其他用户？全部用户？
- **影响的可逆性**：错误状态是否可以恢复？

### 修复方向（非具体代码）
[描述需要建立的新的结构性假设]
示例："服务器应假设请求参数不可信，必须从数据库查询实际所有权关系"
```

### 3. 系统性模式总结

**发现的模式**：
- 哪些原理在该系统中反复出现？
- 这些模式是否存在共同根源？（框架缺陷、设计模式、配置习惯）

**风险演化路径**：
- 当前发现的假设断裂点，可能被如何利用？
- 多个断裂点组合后的系统性风险？

### 4. 修复建议（结构性层面）

**非具体代码建议，而是结构性假设修正**：

| 当前假设 | 建议建立的假设 | 原理 |
|---------|---------------|------|
| "携带有效凭证的请求即用户意志" | "凭证只验证身份，不验证意图；关键操作需额外确认" | 意志不确定 |
| "请求中的资源ID即用户有权访问的资源" | "资源ID只是查询起点，必须验证所有权关系" | 失忆困境 |
| "配置的CORS白名单是安全的" | "跨域信任边界需动态验证，而非静态配置" | 信任重构 |
| "过滤后的输入是安全的" | "不同处理层可能重新解释输入，需在各层验证" | 语义断层 |

## 报告风格指南

**避免**：
- ❌ "发现 SQL 注入漏洞"
- ❌ "存在 XSS 风险"
- ❌ "建议参数化查询"

**改为**：
- ✅ "服务器在推断点X做出的假设（用户输入可直接拼接进查询）与实际情况不符"
- ✅ "用户的意志表达在渲染层被重新解释，导致安全边界断裂"
- ✅ "建议建立新假设：所有外部输入在各处理层都应被视为不可信"

## 交付物

- **Structural Risk Assessment**: 基于四大原理的系统性风险评估
- **Assumption Breakdown Catalog**: 所有被打破的假设及证据
- **Remediation Strategy**: 结构性修复方向（非具体代码）
