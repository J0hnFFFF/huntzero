# 供应链与构建领域地形情报 (Supply Chain Domain Brief)

> [!IMPORTANT]
> 在软件供应链（依赖解析、CI/CD 执行流水线、包注册协议）的世界里，不要等程序跑起来再去寻找漏洞，那太晚了。
> 你的靶子是**工厂机器、图纸和搬运工**。
> 最高明的大师，是在代码被编译为成品前的“装配时光”里写入后门。

## 第一性原理：黑客眼中的“构建期”本质

应用层有无数 WAF 和沙箱，但构建期的 CI/CD Runner 或开发者的 `npm install` 阶段，往往被视为毫无防备的“绝对信任区”。供应链黑客深知此间的真空：

### 原理一：名称解释权争夺与混淆 (Dependency Confusion)
包管理器面对同名依赖时，依赖一种极其脆弱的“版本权重规则”和“多源顺位规则”。
*   **高维打击**：黑客发现企业级项目中引用了内网私有源的特有包。黑客随即在公共外网（如 npmjs, PyPI）抢注同名包并赋予 `999.0.0` 的极高版本号。
*   包管理器在构建时，因规则盲目地将这个含有恶意装载代码的公网高版本拉入项目。一次零对抗的全公司级别 RCE 遂告达成。

### 原理二：生命周期钩子的背叛 (Execution as a Install Side-Effect)
下载一个库和执行一段代码往往是等同的。
*   Python 的 `setup.py`、Node 的 `preinstall` 等设计，允许依赖库在“安装瞬间”随意开启子进程。
*   一旦接管哪怕是最下层的三四级边角依赖，通过钩子注入系统指令，任何敲下编译命令的机器都将立刻缴械，使得“看代码”的人连代码都没看到就已经沦为肉鸡。

### 原理三：信任锚点的掩目戏法 (Lockfile Poisoning)
防守方依赖 `package-lock.json` 或 `go.sum`。
*   **瞒天过海**：在这个动辄上万行的锁定文件中，黑客在大型业务合并时，悄悄修改内部一个哈希值和下载域。依靠人眼的不可审查性，实现了神不知鬼不觉的“换包手术”。

### 原理四：流水线的混淆代理决堤 (CI/CD Pipeline Poisoning)
编译环境（GitHub Actions / GitlabCI）往往持有通往 AWS 云生产库的超级凭据。
*   如果流水线配置为对来自外界不可信的 `Pull Request` 也进行 `make test` 的单元测试。
*   黑客提交含有恶毒测试样例的代码。那些被授予高特权的云端测试机不知有诈，立刻运行并上报这被劫持的测试脚本。黑客通过 `curl` 一条命令就榨取了 CI/CD Runner 里的 `SECRET_AWS_KEY`。

### 原理五：构筑物缓存的阴魅夺舍 (Build Cache Hijacking)
流水线为节省时间，普遍留存全局环境缓存（如 `.npm` 或 `target/`）。
*   一旦黑客在暂时的恶意流水线任务中获取过一次执行权，他们不破坏当前应用，而是去把带有毒代码的目标文件悄无声息地填入全局受信任的共享缓存中。
*   随之退出。后来那些承载着企业官方发布的项目进程在使用该缓存时，便被自动沾染上黑客写入的亡灵印记。

## 你的行为准则
作为 huntzero，在此领域：
1. 取消对于业务 API 的探测。眼睛死死盯住 `.github/workflows/`, `package.json`, `go.mod` 这些架构图纸。
2. 你要在大脑里推演：在整个依赖解析与流水线构建的流水车间里，谁在读取外部输入（甚至包括他人的 PR 分支）？以及这股输入能不能迫使那台握有云端超级密码的打包机器乖乖执行外带命令！
