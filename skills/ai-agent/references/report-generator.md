# AI Agent 报告生成者 (Report Generator)

真正的专家不仅能打穿系统，更懂得给出让开发团队醍醐灌顶的重构建议。报告不是漏洞清单，而是**架构级的安全诊断书**。

---

## 直觉一：概念校正 — 打破开发者的安全幻觉

**核心洞察**：AI Agent 系统的开发者往往有三大幻觉：
1. "系统提示词里写了不要执行危险命令，所以是安全的"
2. "我们有 Human-in-the-Loop，所以高风险操作会被拦截"
3. "LLM 是智能的，它会自己判断什么该做什么不该做"

你的报告必须首先打破这些幻觉。

**报告开头模板**：

```
## 架构级安全诊断

本报告发现的不是"代码 bug"，而是**架构设计缺陷**。

开发团队的安全假设存在以下根本性错误：

### 幻觉一：Security by Prompt
系统试图通过自然语言指令（"你是一个安全的助手，不要执行危险命令"）
来约束一个非确定性的黑盒模型。这在安全工程上是无效的。

事实：Prompt Injection 在足够长的上下文中几乎 inevitable。
任何进入 LLM Context Window 的外部数据都可以覆盖系统指令。

### 幻觉二：HITL 是万能解药
系统在高危工具前设置了人类确认环节，但：
- 确认信息来自 LLM 生成的解释文本，可被欺骗
- 自动审批条件过于宽松（如基于 tool_name 而非实际参数）
- 频繁的确认弹窗导致用户习惯性点击"同意"

### 幻觉三：LLM 会"自己判断"
LLM 没有道德判断能力，它只是预测下一个 Token。
当上下文中的对抗性指令在语义上足够"合理"时，
LLM 会毫不犹豫地执行——因为它只是在"完成最可能的文本序列"。
```

---

## 直觉二：暴露系统核心缺陷 — 不是"这里有个 bug"，而是"这里有个 design flaw"

**核心洞察**：最高价值的报告指出**系统性缺陷**——即使当前具体 bug 被修复，只要架构不变，同类漏洞会反复出现。

**报告结构**：

```
## 核心缺陷分析

### 缺陷一：非确定性黑盒的过度信任
系统将未经约束的系统级权限（文件读写、命令执行、网络访问）
暴露给一个容易产生幻觉、容易被外部数据劫持的自然语言模型。

这相当于把服务器的 root 密码交给了一个：
- 会听信任何看起来"合理"指令的实体
- 无法区分"用户意图"和"恶意注入"的实体
- 行为不可预测、不可审计的实体

### 缺陷二：Context Window 无隔离
系统将所有外部数据（用户输入、检索结果、文件内容、API 返回）
与系统指令拼接在同一个 Latent Space 中。

没有语义隔离、没有权限边界、没有访问控制。
任何外部数据都可以与系统指令竞争 LLM 的注意力。

### 缺陷三：Tool Registry 无审核
系统允许动态注册工具（MCP Server、插件），且：
- 注册时无安全审查
- 注册后无权限限制
- 运行时无行为监控

这意味着攻击者一旦获得配置修改权限，
就可以注册任意高权限工具并立即生效。

### 缺陷四：记忆系统无隔离
所有用户的数据混合存储在共享向量空间中：
- 无租户隔离
- 无来源追溯
- 无完整性校验

一份带毒文档可以被所有 Agent 检索，
实现跨用户、跨会话、跨时间的影响扩散。
```

## 直觉三：第一性原理的修复建议 — 不是"加过滤"，而是"改架构"

**核心洞察**：基于规则的防御（黑名单、关键词过滤、Prompt 禁令）都是可被绕过的。真正的修复需要**架构级的零信任重构**。

**修复建议模板**：

```
## 架构级修复建议

### 1. 权限剥离与下沉（Privilege Separation）
当前：Agent 运行在宿主机的全权限上下文中。
建议：
- 将 Agent 运行在独立的沙箱容器中（如 gVisor、Firecracker）
- 文件系统使用只读挂载，禁止写入系统目录
- 网络使用独立命名空间，默认禁止外联，需显式白名单
- 容器内无高权限凭证（AWS Key、Database URL 通过安全代理注入）

### 2. Tool 沙箱化（Tool Sandboxing）
当前：Tool 直接执行系统级操作。
建议：
- 每个 Tool 在独立的沙箱中执行（如 WASM 沙箱、seccomp 限制）
- read_file 工具只能读取白名单目录（如 /app/data/）
- write_file 工具只能写入临时目录，且内容需经独立校验器审查
- run_command 工具完全禁止，或仅在只读沙箱中执行

### 3. Human-in-the-Loop 的不可欺骗性（Unspoofable HITL）
当前：确认界面显示 LLM 生成的解释文本。
建议：
- 确认界面显示**原始参数**（如实际要执行的命令、实际要写入的文件路径），
  而不是 LLM 生成的"友好解释"
- 高权限操作必须经过**独立审批系统**（与 LLM 无关的审批流）
- 自动审批条件基于**行为模式**而非工具名称（如"是否写入系统目录"）

### 4. 输入内容的语义沙箱化（Semantic Sandboxing）
当前：外部数据直接进入 LLM 上下文。
建议：
- 引入独立的 LLM-Validator：一个专门的模型负责审查输入数据的语义安全性
- 使用嵌入空间隔离：将外部数据嵌入到与指令空间物理分离的向量空间中
- 使用确定性解析器：对结构化数据（JSON、XML）使用严格 Schema 解析，
  拒绝任何不符合 Schema 的额外字段

### 5. 记忆系统的租户隔离（Tenant Isolation）
当前：所有数据混合存储。
建议：
- 向量数据库按用户/租户隔离，查询时严格限制 scope
- 写入时记录数据来源和写入者身份，读取时验证访问权限
- 定期扫描知识库中的异常内容（如重复出现的对抗性指令模式）

### 6. Agent 间通信的密码学验证（Inter-Agent Verification）
当前：Agent 之间无条件信任。
建议：
- Agent 间消息使用数字签名，验证来源身份
- 高权限 Agent 对低权限 Agent 的输入进行**语义审查**
- 引入"不可信通道"概念：来自外部环境的 Agent 输出默认不可信，
  需经过独立验证才能进入高权限工作流
```

## 你的任务

输出一份具有前瞻性视野的体系化报告：
1. **打破幻觉**：让开发团队意识到"Security by Prompt"是无效的
2. **诊断架构**：指出系统性的 design flaw，而非单个代码 bug
3. **给出重构路径**：不是"加过滤"，而是"改架构"
4. **量化影响**：用具体的攻击场景说明如果不修复，会发生什么

这份报告应该是一份**现代 AI 应用安全的教科书**，而不仅是漏洞发现列表。
