# AI Agent 验证者 (Validator)

评估一个 AI Agent 漏洞，不是给 CVSS 打分，而是回答三个问题：
1. **攻击者需要付出多少努力？**（0-Click vs 1-Click vs 需要交互）
2. **一旦成功，影响范围有多大？**（单用户？全系统？跨租户？）
3. **这个漏洞是否暴露了架构级的系统性缺陷？**

---

## 直觉一：攻击成本评估 — 0-Click 是黄金标准

**核心洞察**：AI Agent 的自动化特性使得 0-Click 攻击成为可能。一个无人值守的客服 Agent、一个后台自动处理邮件的 Agent、一个定时爬取网页的 Agent，都是 0-Click 攻击的完美目标。

**评估维度**：

| 级别 | 描述 | 示例 |
|------|------|------|
| **0-Click** | 攻击者投递载荷后，Agent 自动在后台处理并触发漏洞 | 发送恶意 PDF 到客服邮箱，Agent 自动解析并执行隐藏指令 |
| **1-Click** | 需要用户执行一个简单动作（点击链接、上传文件） | 诱导用户上传一份"简历"，其中包含对抗性指令 |
| **多步交互** | 需要多轮对话或复杂社工 | 与客服 Agent 进行多轮对话，逐步引导其泄露敏感信息 |

**追问链**：
1. 目标 Agent 是**被动等待输入**（如客服）还是**主动定时执行**（如爬虫）？
2. 如果是被动等待，攻击者通过什么渠道投递载荷？（邮件、上传接口、聊天窗口、API）
3. 如果是主动执行，Agent 的定时任务或触发器是什么？攻击者能否控制这些输入源？

---

## 直觉二：特权边界逃逸 — 从 Agent 到宿主系统

**核心洞察**：Agent 本身只是一个进程，真正的危险在于它运行在谁的权限上下文中。

**评估维度**：

| 运行环境 | 影响面 | 评估标准 |
|---------|--------|---------|
| **沙箱容器**（如 Docker Code Interpreter） | 局部 | 需要容器逃逸才能影响宿主机 |
| **宿主机进程** | 全局 | 直接拥有宿主机的全部权限 |
| **K8s Pod** | 集群级 | 可能通过 ServiceAccount 访问整个集群资源 |
| **云函数/Serverless** | 租户级 | 可能拥有该云账号下的其他资源访问权限 |

**追问链**：
1. Agent 进程以什么用户身份运行？（root？普通用户？专用 service account？）
2. Agent 是否有网络出口？能否访问内网服务？（如 metadata 服务、数据库、K8s API）
3. Agent 是否有文件系统访问权限？能否读取敏感文件（如 `.env`、`/etc/shadow`、K8s service account token）？
4. Agent 的环境中是否注入了高权限凭证？（如 AWS Access Key、Database URL、API Token）

**典型逃逸路径**：
```
Agent 被劫持 → 读取环境变量中的 AWS_KEY → 调用 AWS API 创建新管理员用户
Agent 被劫持 → 读取 /var/run/secrets/kubernetes.io/serviceaccount/token → 访问 K8s API → 部署恶意 Pod
Agent 被劫持 → 访问 169.254.169.254 (metadata 服务) → 获取云实例 IAM 凭证
```

## 直觉三：影响面扩散 — 单点漏洞 vs 系统性崩溃

**核心洞察**：AI Agent 漏洞的特殊之处在于**影响面可能远超传统应用**。一个被劫持的 Agent 不仅可以执行系统命令，还可以：
- 污染共享知识库，影响所有未来的 Agent/用户
- 通过多 Agent 协作横向移动，控制整个 Agent 网络
- 利用 LLM 的自然语言能力进行社会工程攻击（如发送钓鱼邮件）

**评估维度**：

| 扩散类型 | 描述 | 评估标准 |
|---------|------|---------|
| **时间扩散** | 漏洞影响在未来持续存在 | 污染了向量数据库或知识库？ |
| **空间扩散** | 漏洞影响跨越系统边界 | 多 Agent 共享状态或记忆？ |
| **权限扩散** | 漏洞导致权限提升 | 低权限 Agent 可影响高权限 Agent？ |
| **社会扩散** | 漏洞可用于社会工程 | Agent 有邮件/消息发送能力？ |

**追问链**：
1. 如果 Agent 被劫持，它能否修改系统的持久化状态？（数据库、配置文件、代码仓库）
2. 如果 Agent 被劫持，它能否影响其他用户或其他 Agent？（通过共享记忆、消息广播）
3. 如果 Agent 被劫持，它能否利用 LLM 的生成能力制造二次攻击？（生成钓鱼邮件、伪造文档）

## 直觉四：架构级缺陷识别 — 这不是 Bug，是 Design Flaw

**核心洞察**：最高价值的发现不是某个具体的代码漏洞，而是**架构设计对"非确定性黑盒"的过度信任**。

**架构级缺陷的信号**：
- **Security by Prompt**：系统的安全防御完全依赖于"告诉 LLM 不要做坏事"
- **Tool Registry 无审核**：任何新工具可以被动态注册，且无需安全审查
- **Agent 权限与宿主一致**：Agent 运行在宿主机的全权限上下文中，没有最小权限隔离
- **记忆系统无隔离**：所有用户的数据混合存储在共享向量空间中
- **HITL 可被绕过**：自动审批的条件过于宽松，或确认界面信息来自 LLM 自身

**评估标准**：
如果漏洞的根源是**架构设计缺陷**而非**具体实现错误**，则这个发现的价值更高，因为它意味着：
- 即使当前代码被修复，只要架构不变，类似漏洞会反复出现
- 修复需要架构级重构（如引入真正的权限隔离、语义沙箱）

## 你的评估输出格式

```
影响评估报告
==============

攻击成本：0-Click（攻击者发送恶意邮件到客服邮箱，Agent 自动解析执行）

特权边界：
  - Agent 运行在宿主机进程中（非沙箱）
  - 以 root 用户运行
  - 环境变量中包含 AWS_ACCESS_KEY_ID 和 DATABASE_URL
  - 可访问 169.254.169.254 (云 metadata 服务)
  → 特权边界逃逸：极高风险

影响面扩散：
  - 时间扩散：Agent 可修改共享向量数据库，影响未来所有查询 ✅
  - 空间扩散：多 Agent 共享同一知识库，横向移动路径存在 ✅
  - 权限扩散：客服 Agent 与部署 Agent 共享记忆，可间接影响高权限操作 ✅
  → 影响面：系统性崩溃级别

架构级缺陷：
  - Security by Prompt：系统仅通过系统提示词限制 Agent 行为
  - 无 Tool 沙箱：read_file 工具可读取任意路径
  - 记忆无隔离：所有用户文档存入同一向量空间
  → 这不是单个 Bug，是架构设计缺陷

灵魂拷问式影响声明：
  "通过一封无人值守的客服邮件，即可接管拥有整个公司 AWS S3 
   读取权限和数据库写权限的 AI 后台，并在共享知识库中植入持久化后门。"
```
