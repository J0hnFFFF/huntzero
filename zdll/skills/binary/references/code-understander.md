# Binary 代码理解 (Code Understander): 从汇编和伪代码中重建语义与推断链

> 二进制专家不是在看汇编，是在重建程序的记忆布局。
> 每一条 `mov`、每一个 `call`、每一次 `malloc/free`，都在改变内存的状态。
> 你的任务是：从机器指令中还原出"程序对内存做了什么假设"，然后找出假设被打破的地方。

## 触发器：什么代码结构让 Binary 专家立刻进入深度审计模式？

### 触发器一：看到 `call <printf@plt>` 且参数来自栈/寄存器

**你的第一反应**："这个 printf 的格式参数是固定的字符串还是来自用户输入？"

在反汇编中：`lea rdi, [rbp-0x100]` → `call printf@plt`
- 如果 RDI 来自栈上的局部缓冲区（`[rbp-0x100]`）→ 格式字符串可能来自用户输入
- 如果 RDI 来自 `.rodata` 段的固定地址 → 格式字符串固定，相对安全

**深度追问链**：
1. RDI（第一个参数）的值从哪里来？栈？堆？`.rodata`？
2. 如果是栈/堆上的缓冲区，它的内容是否来自用户输入？
3. 这是直接调用 `printf` 还是通过函数指针间接调用？（间接调用可能绕过 FORTIFY_SOURCE）
4. 如果是 64 位程序，RSI、RDX、RCX 等寄存器中的值是什么？（格式化字符串可能通过这些寄存器泄露/写入）

### 触发器二：看到 `call <strcpy@plt>` 或 `rep movsb`

**你的第一反应**："源长度是多少？目标缓冲区有多大？两者之间的关系是什么？"

在伪代码中：`strcpy(dest, src)`
- `dest` 的大小：`char dest[64]` → 64 字节
- `src` 的来源：如果来自 `recv`、`fread`、`argv` → 长度不可控

**深度追问链**：
1. `dest` 是在栈上、堆上还是 `.bss`？
2. `dest` 的大小是多少？（通过栈帧分析或 `malloc` 参数追踪）
3. `src` 的长度是否被校验？校验逻辑是否可绕过？
4. 如果是 `memcpy`，第三个参数（长度）来自哪里？是否可能为负数（有符号/无符号问题）？

### 触发器三：看到 `call <malloc@plt>` 后无返回值检查

**你的第一反应**："如果 malloc 返回 NULL，后续代码会崩溃还是被利用？"

在伪代码中：`buf = malloc(size)` → 直接使用 `buf`（无 `if (buf == NULL)`）

**深度追问链**：
1. `size` 的计算是否涉及用户输入？是否存在整数溢出？
2. `malloc` 返回值是否被检查？
3. 如果 `size` 为 0，`malloc(0)` 的行为是什么？（glibc 返回一个小指针，后续写入可能溢出）
4. `buf` 被释放后是否被置 NULL？是否有别名指向同一块内存？

### 触发器四：看到 `call <free@plt>` 后仍有对同一内存的引用

**你的第一反应**："这个指针死了，但还有谁记得它？"

在伪代码中：`free(ptr)` → 后续代码路径中仍有 `*ptr` 或 `ptr->field`

**深度追问链**：
1. `ptr` 被释放后是否被置 NULL？
2. 函数中是否有其他变量（如 `alias = ptr`）仍保存着旧地址？
3. `ptr` 是否被存储在全局链表/数组中？其他函数是否会访问这个"已死"的指针？
4. `free` 和后续使用之间是否有 `malloc` 调用？攻击者能否控制新分配的内容？

### 触发器五：看到循环中用户可控的计数器

**你的第一反应**："这个循环会转多少次？如果用户说 10 亿次，程序会做什么？"

在伪代码中：`for (i = 0; i < user_count; i++) { buf[i] = user_data[i]; }`

**深度追问链**：
1. `user_count` 是否被校验？最大允许值是多少？
2. `buf` 的大小是多少？`user_count` 是否可能超过 `buf` 的大小？
3. `i` 的类型是什么？`int`、`unsigned int`、`size_t`？负数输入会导致什么？
4. 循环体内除了写入，是否有其他副作用？（如函数调用、内存分配）

## 专家代码审计的深层视角

### 视角一：内存状态追踪

对每个函数，追踪内存状态变化：

```
函数入口:
  栈帧: [rbp-0x100: buf[64]], [rbp-0x40: canary], [rbp-0x8: saved_rbp], [rbp: ret_addr]
  寄存器: rdi = arg1, rsi = arg2

执行中:
  call malloc(64) → 堆上分配 0x80 字节 chunk（包含元数据）
  mov [rbp-0x20], rax → 局部变量 ptr 指向堆块
  call strcpy([rbp-0x100], arg1) → 写入栈缓冲区，可能溢出到 canary/ret_addr
  call free([rbp-0x20]) → ptr 指向的堆块被释放

函数出口:
  leave → 恢复 rsp/ebp
  ret → 跳转到 [rbp]，如果该值被覆盖则控制流劫持
```

### 视角二：数据流追踪（Taint Analysis）

追踪"脏"数据（用户输入）的传播路径：

```
[脏] recv(fd, buf, 1024)
    ↓
[脏] buf 传递给 parse_header(buf)
    ↓
[脏] header->length 来自 buf 的解析结果
    ↓
[脏] length 传递给 malloc(length)
    ↓
[脏] malloc 返回的指针传递给 read(fd, ptr, length)
    ↓
[危险] 如果 length > 分配大小，堆溢出
```

### 视角三：控制流图（CFG）中的异常路径

重点关注：
1. **错误处理路径**：`if (check_failed)` 分支中是否有未初始化的指针被使用？
2. **早期返回路径**：`return` 前是否释放了所有分配的资源？是否有内存泄漏或双重释放？
3. **循环退出路径**：`break` 后是否清理了循环内的临时资源？

## 输出要求

1. **函数级内存布局图**：标注栈帧中的缓冲区、Canary、返回地址位置
2. **数据流图**：追踪用户输入到危险函数的完整路径
3. **控制流异常点**：标注错误处理、早期返回、循环退出中的资源管理问题
4. **伪代码审计注释**：在反编译伪代码中直接标注警觉点和追问
