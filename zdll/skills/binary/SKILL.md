# 二进制程序地形情报 (Binary Domain Brief)

> [!IMPORTANT]
> V7 模式：本文件是 **领域地形知识**，不是执行步骤。
> Cerebrum 读取后应基于第一性原理自主决定分析路径。

## 二进制程序的本质结构

二进制程序是**对内存布局的直接操控系统**，分析的核心挑战在于：

- **主要 Invariant**：程序在任意时刻对内存的读写都应在其合法分配范围内。控制流转移只应到合法的代码段地址。
- **信息不对称**：源码已不存在。分析必须从汇编/伪代码重建语义——工具是眼睛，不是答案。
- **核心状态**：栈帧（局部变量、返回地址）、堆布局（chunk 分配图）、寄存器/标志位
- **核心转换**：函数调用改变栈状态，`malloc/free` 改变堆布局，条件分支改变控制流路径

## 已知的结构性地形

### 1. 静态分析入口（从黑盒到语义重建）
建立目标静态画像的关键观察点：
- **文件类型与架构**：ELF/PE 类型、CPU 架构、端序——决定后续所有工具链选型
- **安全机制**：NX/ASLR/PIE/Stack Canary/RELRO 配置——是攻击路径的硬性约束边界
- **符号信息**：Strip 程度决定分析起点；通过签名库或 AI 推断恢复函数语义
- **导入表**：危险函数 xref 分析（`strcpy`, `system`, `memcpy`, `recv`, `sprintf`）

### 2. 内存安全 Invariant 的声明位置
- **堆分配器边界**：`malloc(n)` 返回的缓冲区，上层代码是否严格遵守了 `n` 字节写入限制？
- **栈帧大小**：局部数组声明大小 vs 写入时长度计算——整数溢出是边界突破的主要触发源
- **释放后使用**：指针归零是否在所有代码路径下均发生？是否存在保存了原始指针的别名？

### 3. 动态分析的关键状态观察点
- **协议解析器**：`recv()` 后的协议帧解析器是核心 Fuzzing 目标——格式验证与内存分配的时序关系
- **格式字符串处理**：用户控制的字符串直接作为 `printf` 格式参数的调用链
- **整数运算边界**：有符号/无符号转换、截断（`int` to `short`）、乘法溢出——三大 OOB Write 数学来源

## 已知的 Invariant 失效模式

| Invariant 声明 | 常见失效来源 | 分析方法 |
|----------------|------------|---------|
| "写入不超过分配大小" | 整数溢出导致长度计算错误 | 伪代码 + 整数类型追踪 |
| "释放后指针不再被引用" | 存在别名或容器缓存了原始指针 | 数据流追踪 + ASAN |
| "控制流只跳转到合法地址" | 函数指针未校验直接来自用户数据 | 交叉引用分析 (xrefs) |
| "栈返回地址不可覆盖" | 无 Canary + OOB Write 长度可控 | checksec + 溢出长度分析 |

## 项目类型对严重性的影响

| 项目类型 | 示例 | 严重性调整 |
|---------|------|-----------|
| **独立程序** | 网络服务、CLI 工具 | 直接受外部输入，**标准严重性** |
| **动态库 (.so/.dll)** | libpng, openssl, zlib | 需调用者传入恶意数据，严重性 **-1 级** |
| **内核模块** | 驱动、文件系统模块 | 内核态漏洞严重性 **+1 级** |
| **固件/嵌入式** | IoT 设备固件 | 远程可达则严重性 HIGH+，仅物理访问则 LOW |
